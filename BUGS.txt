[Б-1]  СВОЁ СООБЩЕНИЕ ВСЕГДА ДУБЛИРУЕТСЯ — самая заметная поломка
───────────────────────────────────────────────────────────────────────────────
Где:    src/ui/input.rs:82-98  (handle_input)
        src/app.rs:232-258    (ToApp::Message)

Что:    handle_input сначала кладёт сообщение в список САМ:
            self.messages.entry(cid).or_default().push(Arc::new(ChatMessage {
                id: String::new(),          // ← id пустой!
                ...
            }));
        потом отправляет его в Discord (ToGateway::Send).

        Discord отвечает событием MESSAGE_CREATE, и гейтвей (gateway.rs:754)
        шлёт то же самое в ToApp::Message. Там проверка на дубликат
        (app.rs:238):
            let duplicate = !msg.id.is_empty()
                && self.messages.get(&cid).is_some_and(|e| e.iter().rev()
                    .any(|m| m.id == msg.id));
        У присланного от Discord id настоящий, у локального — пустая строка.
        Совпадения не происходит → сообщение добавляется ВТОРЫМ.

Симптом: каждое отправленное сообщение видно в чате дважды. Тот самый
        «фикс задвоения», который 0.5.1 сделал для истории (3937d0d), не
        покрывает локальное эхо — это другой путь.

Почему не поймано тестами: geometry_tests кормят приложение сообщениями
        напрямую из ToApp, а handle_input в тестах геометрии не вызывается.

Как чинить (идея): на отправке сразу завести id-заглушку и на его замену,
        либо запоминать (channel_id, текст, время отправки) и при MESSAGE_CREATE
        с author_id == self.user_id заменять локальное эхо, а не добавлять
        новое. Второе надёжнее: текст у Discord может обрезаться (2000 символов).

[Б-4]  ТИХОЕ ПОВТОРЕНИЕ СТРАНИЦЫ ПРИ БЫСТРЫХ КЛИКАХ ПО КАНАЛАМ
───────────────────────────────────────────────────────────────────────────────
Где:    src/gateway.rs:882-900 (обработка ToGateway::FetchHistory)

Что:    Защита от дублей (history_inflight) устроена так, что второй запрос
        по тому же каналу просто ОТБРАСЫВАЕТСЯ:
            if !busy.insert(cid.clone()) {
                ... "History for ... already in flight, skipping"
                return;
            }
        Сценарий: клик по каналу A → клик по B → клик по A. Второй запрос по A

        переключения) — поведение зависит от того, успеет ли он вернуться.
        В худшем случае — тот же вечный спиннер, что в Б-2.

Как чинить: дедуплицировать не по каналу, а по (канал, before); при
        отбрасывании дубля всё равно подтверждать приложение, что запрос
        «в работе», иначе оно ждёт события, которого не будет.

Где:    src/crypto.rs:97-104 (mask_token)

Твик: `token.chars().take(4)` / `chars().rev().take(4)`, либо проверять
      `is_char_boundary` перед срезом. То же самое касается
      app.rs:576-583 short_time (режет `&t[11..16]` по байтам) — там timestamp
      приходит из de_text, который принимает ЛЮБОЕ значение JSON, так что
      не-ASCII во входных данных возможен.

      15 кадров, как FRAME). Это же избавит от eprintln на 20 Гц.

[Б-14] РАЗМЕР КАРТИНКИ ИЗ ИСТОРИИ НЕ ЧИТАЕТСЯ ВООБЩЕ — ФИКС 0.5.1 НЕ РАБОТАЕТ
───────────────────────────────────────────────────────────────────────────────
Это самая крупная находка из обоих проходов.

Где:    src/gateway.rs:217-227   (struct RawAttachment)
        src/gateway.rs:199-201   (de_opt_size)
        src/models.rs:113-125    (image_size_of)
        src/gateway.rs:390        (parse_message_value — живой путь)

Что:    Поле вложения объявлено так:
            #[serde(default, deserialize_with = "de_opt_size")]
            size: Option<[u32; 2]>,

        То есть serde читает JSON-поле `"size"` и скармливает его десериализатору,
        который вызывает image_size_of. А image_size_of ищет ВНУТРИ значения
        ключи "width" и "height":

            let num = |k: &str| match v.get(k) { ... };
            match (num("width"), num("height")) { ... }

        Discord шлёт `"size": 123456` — это РАЗМЕР В БАЙТАХ, число. Внутри
        числа ключей "width"/"height" нет, `Value::get` на числе возвращает
        None, и image_size_of возвращает None. Всегда.

        Настоящие `"width": 1600, "height": 1200` Discord шлёт РЯДОМ с
        "size", отдельными полями объекта. Но в RawAttachment их нет вообще,
        а serde неизвестные поля молча выбрасывает.

        Итог: Attachment.size у ЛЮБОГО сообщения из истории = None. Всегда.

        При этом живой путь (parse_message_value:390) делает
            size: image_size_of(a),
        где `a` — весь объект вложения. Там width/height читаются правильно.

        То есть два пути разбора одного и того же сообщения дают разный
        результат. Проверено отдельным прогоном с фикстурой из самого
        тестового набора (gateway.rs:982-992 — там эти поля есть):

            история (RawAttachment.size)  = None
            живое   (image_size_of(att)) = Some([1600, 1200])
            >>> РАСХОЖДЕНИЕ ПОДТВЕРЖДЕНО

Последствия:

  1) ГЛАВНОЕ. ROADMAP 0.5.1 пишет: «Картинка меняла высоту сообщения на
     ±180 px в момент загрузки. Теперь место резервируется по размерам,
     которые Discord присылает со ссылкой». Так вот: для ИСТОРИИ это не
     работает. history_known = None → reserved_size даёт заглушку
     360x180, а после загрузки реальная картинка встаёт по своим размерам
     (до 360x360). Прыжок на ±180 px возвращается.

  2) Именно на истории это и видно: открытие канала = 50 сообщений из
     fetch_history_page, то есть 100% сообщений с картинками в канале
     грузятся без размера. Живое сообщение (то, что пришло само, пока
     смотришь канал) — единственное, где размер есть.

  3) Ломается ровно то, ради чего писалась виртуализация: высота в
     msg_offsets занижена на 180 px на каждое такое сообщение, значит
     полоса прокрутки и позиции всех сообщений ниже неверны, и при
     прокрутке список «прыгает» именно там, где много картинок.

  4) Тест, который специально написан, чтобы ловить расхождение двух
     путей разбора (history_and_live_parse_agree, gateway.rs:1051),
     сравнивает url и description — но НЕ size. Расхождение прямо перед
     глазами у теста, и он его не замечает. Тест на фикстуре
     history_page_maps_all_used_fields тоже не проверяет a.size.

  5) Мелкая, но из того же места: у ЭМБЕДОВ путь другой и правильный
     (RawEmbed.image: RawImage, там поле называется `size`, но
     deserialize_with тот же de_opt_size... стоп, проверял: у эмбеда
     image_size = image.and_then(|i| i.size) — тот же de_opt_size на
     JSON-поле "size" эмбеда, которого там тоже нет). Значит эмбеды с
     картинками тоже всегда без размера. Правда, эмбеды в draw_message
     рисуются по-другому, прыжка там может и не быть.

Как чинить: завести в RawAttachment отдельные поля
            #[serde(default, deserialize_with = "de_opt_size")]
            width: Option<[u32;2]>,   // ← нет, де_opt_size ждёт объект
        Точнее — либо переименовать поле в `size` → «width/height», т.е.
        принимать объект `{width, height}` (как делает image_size_of), либо
        добавить десериализатор, который берёт САМ объект вложения и зовёт
        image_size_of(a) — то есть сделать живой и исторический путь
        буквально одной строкой. Второе надёжнее: тогда расхождение между
        путями физически невозможно.

 ЧАСТЬ 6. ЧТО ПЕРЕПРОВЕРЕНО ВО ВТОРОМ ПРОХОДЕ И ОКАЗАЛОСО НЕ БАГОМ
═══════════════════════════════════════════════════════════════════════════════

Чтобы не выглядело так, будто я перебирал и цеплялся за каждое. Вот что
специально проверил и снял:

1. Enter не отправляет сообщение — СНЯТО. Исходники egui 0.31 предлагают
   ровно этот приём (lost_focus + key_pressed) как официальный, и
   документируют, что в singleline Enter снимает фокус с виджета.

2. Задержка кадров GIF в 1000 раз меньше нужной — СНЯТО. Заподозрил формулу
   в media.rs:247-252:
       let (num, den) = fr.delay().numer_denom_ms();
       let secs = if den == 0 { 0.1 } else { (num as f64 / den as f64) / 1000.0 };
   Перечитал image 0.25 (src/animation.rs:205): numer_denom_ms возвращает
   задержку В МИЛЛИСЕКУНДАХ, то есть num/den — это миллисекунды. Деление на
   1000 как раз переводит их в секунды, и переменная названа верно. Для
   кадра с задержкой 100 мс получается num=100, den=1000 → secs = 0.1,
   то есть ровно то, что нужно. Формула верна.

   Отдельно отмечу, что .max(0.02) делает её устойчивой к любой ошибке
   масштаба, так что тут двойная защита. Не баг.

3. `stick_to_bottom` и `vertical_scroll_offset` в одном ScrollArea — НЕ
   конфликтуют. Проверил по scroll_area.rs:1010: при включённом
   stick_to_end и scroll_stuck_to_end egui принудительно ставит своё
   смещение, но это происходит ПОСЛЕ того, как клиент уже нарисовал своё
   окно; спасает именно OVERSCAN = 600, как и в [Т-20].

4. Поле в сообщении может оказаться пустой строкой и сломать расчёт
   before — СНЯТО. request_older_history отдельно проверяет
   oldest.is_empty() и ставит history_exhausted.

5. Индекс self.channels[selected_channel] может выйти за границы — СНЯТО.
   switch_account единственный места, где channels.clear(), и там же
   selected_channel = None. current_channel_id использует .get().

6. save_accounts с пустым паролем пишет токены открытым текстом — СНЯТО.
   encrypt_accounts возвращает None на пустом пароле, save_accounts при
   None просто ничего не пишет. Токен на диск без пароля не утекает.

7. Поток загрузки картинки может уронить счётчик слотов — СНЯТО.
   ImageSlot на Drop (media.rs:97-103) ловит и падение. Для аватарок
   счётчик тоже снимается на всех путях, кроме падения потока — но там
   падать нечему (никакого .unwrap без обработки), так что это не баг.

8. Событие закрытия read-задачи обрабатывается — СНЯТО, __CLOSE__
   действительно доезжает. Проблема не в потере события, а в том, что
   код закрытия не разбирается ([Б-19]).

9. response.lost_focus() у TextEdit в singleline — работает как задумано,
   см. пункт 1.

10. Картинка-эмбед с неизвестным размером — прыжка нет, эмбеды рисуются
    как есть. Находка [Б-14] про вложения, не про эмбеды (хотя и там
    размер не читается — просто последствий пока не видно).
