# TODO — Wyvern

Состояние на 2026-10-02, после 0.5.2 (плюс разбор идей от Claude / DeepSeek /
Gemini).

Правило: здесь только то, что закрывается мелким коммитом и тестом. Крупные
темы (эпики) — одной строкой со ссылкой на [ROADMAP.md](ROADMAP.md), детали
там.

грубая оценка усилий.

## Сделано

- [x] **Разбить `main.rs` на модули** — `app`, `gateway`, `messages`, `models`,
      `media`, `crypto`, `util`, `ui/*`. Поведение сохранено.
- [x] **Меню входа**: токен и локальный пароль в одну строку, галка
      «Запомнить этот аккаунт» снизу, лента сохранённых аккаунтов внизу слева,
      одна подпись «Показать сохранённые аккаунты».
- [x] **Пароль хранилища**: пустое хранилище больше не считается «неверным
      паролем», лишние пробелы прощаются с подсказкой, в ошибке видно путь
      к файлу и когда он менялся.
- [x] **Тесты не трогают настоящий файл** — путь хранилища переопределяется
      в `App`, а не в переменной окружения (тесты идут параллельно).
- [x] **История в чатах**: загрузка больше не блокирует очередь команд
      гейтвея, пагинация берёт `before` от самого старого сообщения
      (были дубли и вчетверо больше запросов), поздний ответ по закрытому
      каналу не снимает «Loading messages…».
- [x] **Убрать отладочную строку из GUI** (`CHAT-AREA w=646 h=1001 …`).
      В лог она осталась, в GUI — нет.
- [x] **Эмбеды**: `Vec<serde_json::Value>` → `{ image_url, description }`.
- [x] **Кэш картинок ограничен байтами, а не числом элементов**: бюджет 48 МБ
      + потолок 32 штуки. Было: 32 картинки по 1536 px = 216 МБ, одна гифка
      добавляла 28 МБ. Стало: кэш не может превысить 48 МБ при любых
      картинках. Это и есть реальный расход текстур, а не только своя
      прикидка: `TextureHandle` освобождает текстуру в egui, когда вытеснение
      уничтожает последнюю ссылку (тест `evicting_a_texture_frees_it_in_egui_too`
      в `src/models.rs`). Неучтённой копии в egui не остаётся.
- [x] **Размеры картинок по отображаемому**: в чате максимум 360×360, значит
      768 px (с запасом на HiDPI) вместо 1536; гифка 448 px вместо 640.
      В кэш влезает 28 картинок вместо 16 в тех же 48 МБ.
- [x] **Потолок на одновременные загрузки картинок** (3 штуки, как у
      аватарок) — раньше на каждую картинку в канале создавался поток, и
      все они одновременно держали декодированные пиксели.
- [x] **Утечка незабранных загрузок**: при смене канала картинки прежнего
      канала навсегда оставались в `pending_images` вместе с
      декодированными пикселями (мегабайты на картинку). Теперь
      получатели сбрасываются, и память освобождается сразу.
- [x] **История разбирается сразу в сообщения** (serde-структуры вместо
      `Vec<serde_json::Value>` на всю страницу). Пик разбора 5.64 → 0.54 МБ,
      аллокаций 52 216 → 4 517. Если формат неожиданный — страница
      разбирается запасным, терпимым способом, чтобы история канала не
      пропала из-за одной странной строки.
- [x] **Живое сообщение и страница истории разбираются одной функцией**
      (`parse_message_value`), тест сверяет их результат: разъехаться они
      больше не могут.
- [x] **Меньше мусора на каждом кадре**: имя, текст и время сообщения
      берутся ссылкой, а не копией; ключ кэша аватарок собирается в один
      буфер; убран отдельный проход по всем сообщениям ради аватарок
      (он всё равно дублировал то, что делает каждая строка); проверка
      «это картинка?» больше не делает `to_lowercase()` и `to_string()`
      на каждый URL на каждом кадре.
- [x] **Списки в боковой панели больше не клонируются на каждом кадре**
      (список каналов гильдии, DM, друзья) — раньше это были тысячи
      аллокаций 20 раз в секунду.
- [x] **Гифки играют целиком**: раньше `collect_frames()`
      распаковывал гифку целиком (500 кадров по 1000×1000 = 2 ГБ), потом
      был жёсткий потолок в 16 кадров — и любая длинная гифка обрывалась
      на середине. Теперь граница по памяти (`MAX_GIF_BYTES`, 32 МБ):
      число кадров считаем по структуре файла, длинную гифку ужимаем, но
      проигрываем до конца.
- [x] **Видимая картинка не вытесняется из кэша**: `BoundedCache` помнит,
      что рисовалось в этом и прошлом кадре (`mark_visible` +
      `begin_frame`), и не выкидывает это. Раньше соседняя только что
      загруженная картинка выбивала видимую, в следующем кадре её качали
      заново — гифка мигала, чат дёргался. Если всё на экране не влезает в
      бюджет — временно живём сверх него.
- [x] **Готовые загрузки больше не копятся**: результат забирался только
      при отрисовке своей картинки, и та, которую успели прокрутить за
      экран, навсегда оставляла в `pending_images` распакованные пиксели.
      На длинном чате с гифками это выросло в 269 МБ RSS. Теперь каждым
      кадром (`reap_pending_images`) всё готовое уходит в кэш, где память
      ограничена бюджетом и LRU; сбор идёт после отрисовки, чтобы вставка
      не вытеснила картинку, которая в этом кадре как раз въехала в окно.
- [x] **Счётчик «n/2000» показывается, только когда есть что считать**:
      на пустом поле «0/2000» выглядел застывшим и ненужным индикатором.
      Место под счётчик зарезервировано всегда, чтобы поле не прыгало по
      ширине на первом набранном (или стёртом) символе.
- [x] **Потолок на размер исходника** (`MAX_SOURCE_PIXELS`, 40 Мпикс):
      распаковка идёт по исходным пикселям, а Discord принимает картинки
      до 10000×10000 (400 МБ на одну). Слишком большая картинка
      отсекается до выделения памяти и помечается как неудачная, вместо
      бесконечного спиннера показывается «не удалось загрузить».
- [x] **Мёртвый код и предупреждения**: 28 предупреждений → 0. Убраны
      неиспользуемые поля (`Attachment.filename/width/height/size`,
      `UserProfile.avatar/discriminator`, `Guild.owner_id`), мёртвые
      `UserUpdate` и `auth_headers`, deprecated `Frame::none()`/`rounding`,
      f32-фолбэки.
- [x] **Дамп сообщений в `/tmp` — только по `WYVERN_DUMP=1`**, лог
      `/tmp/wyvern_layout.log` переезжает на `.1`, когда переваливает за 2 МБ.
- [x] **Замер памяти в тестах** (`src/memcheck.rs`, `cargo test --release --
      -- --ignored --nocapture memcheck`): считающий аллокатор, тот же
      файл копируется в старую версию, числа сравнимы. Замеряет «пол»

- [x] **Слот загрузки картинки больше не утекает (баг «картинки не грузятся
      вообще»).** Потолок на 3 одновременные загрузки был сделан на
      `fetch_add(1) < 3`: при отказе счётчик всё равно увеличивался. За
      пару кадров он уходил за 3 навсегда — опуститься обратко он мог
      только при успешной загрузке, а она уже не начиналась. Слот теперь
      берётся `fetch_update` (счётчик растёт, только если слот достался) и
      отпускается сам (`ImageSlot` на `Drop`), в том числе если поток упал
      на распаковке: падение больше не съедает слот навсегда. Сквозной тест
      с локальным HTTP-сервером грузит 6 картинок при лимите 3: на
      сломанном коде загружались ровно 3, дальше — тишина.
- [x] **История постранично, как в Discord** — 50 сообщений на канал при
      открытии, дальше по мере прокрутки вверх. Протокол разделён на
      `ToApp::History` (заменяет список) и `ToApp::HistoryMore` (вставляется
      в начало), у `ToGateway::FetchHistory` появился `before` — id самого
      старого показанного сообщения. Дошли до начала — `history_exhausted`,
      и клиент больше не ходит в API за пустыми страницами. Потолок на канал
      поднят 300 → 500.
- [x] **Виртуализация списка сообщений** — кэш измеренных высот по id,
      префиксные суммы `msg_offsets`, окно через `partition_point` (деление
      пополам, а не перебор канала) с запасом `OVERSCAN = 600`. Пропущенные
      сообщения не рисуются, но место под них остаётся `add_space`, иначе
      полоса прокрутки врала бы про длину истории. Ключ кэша — id, а не
      индекс: подгрузка вверх его не портит.
- [x] **Вид держится на сообщении, а не на номере строки** (`chat_anchor`) —
      подгрузка истории вверх не выбрасывает читателя. Якорь сбрасывается,
      когда прокрутка уехала мимо подсказки: это значит, что прокрутил
      пользователь.
- [x] **Баг: чат не показывал новые сообщения** (нашли тесты геометрии).
      Якорь брался до перемотки вниз и закреплял вид вверху канала: чат
      открывался на начале истории, а история вверх грузилась повторными
      страницами до потолка. Теперь на кадре, который сам уезжает вниз,
      якорь не берётся, окно считается сразу для низа списка, а «просить
      ещё историю» нельзя, если список целиком влез в окно.
- [x] **Заглушка на месте нескачанной картинки** (`IMAGE_PLACEHOLDER =
      180.0`, в `ui::attachments` рядом с `display_size`) — и оценка высоты,
      и отрисовка считают одно и то же. Без неё высота сообщения скакала
      на сотни пикселей, когда картинка докачивалась.
- [x] **Тесты геометрии чата** (`src/ui/chat.rs`, `mod geometry_tests`) —
      настоящий egui `Context`, 300 сообщений, прокрутка в нескольких
      местах: полоса не врёт про длину истории, при прокрутке не остаётся
      пустот, подгрузка вверх не сдвигает взгляд, новое сообщение тянет
      вниз только из нижнего положения, история запрашивается ровно один
      раз. Такими поломками нельзя поймать по числам аллокаций.
- [x] **Баг: чат копировался при прокрутке вверх** (жалоба на живой клиент).
      Discord отдаёт страницу истории от новых к старым, а приложение хранило
      её как прислали. Из-за этого первой в списке была самая новая строка, и
      `before` для догрузки вверх уходил от неё — Discord отвечал той же
      страницей, она подставлялась в начало, и список рос копиями одних и тех же
      сообщений до потолка в 500. Попутно ломалось и `trim_messages`: она
      выбрасывает начало списка, а начало — это были самые новые сообщения.
      Теперь `apply_history` разворачивает страницу, и контракт записан в
      `ToApp::History`: страница приходит от новых к старым, список живёт от
      старых к новым.
- [x] **Живое сообщение могло задвоиться**: гейтвей шлёт живую копию всего, что
      появилось после подписки, а та же строка к этому моменту уже успела
      попасть в страницу истории. Дубль рисуется дважды. Теперь повтор по `id`
      пропускается; сообщения без `id` (своё, пока Discord не подтвердил
      отправку) проверку проходят как раньше.
- [x] **Урок про тесты с фикстурами**: `older_page_is_prepended_without_duplicates`
      кормил приложение страницами в порядке «от старых к новых», хотя Discord
      так не отдаёт. Тест был зелёным и закреплял неверное допущение — ровно
      так же, как работала программа. Теперь фикстуры повторяют настоящий
      порядок страниц, а главное утверждение в тесте стало строгим: список
      должен быть ровно m1..m100 по порядку, без единого повтора.
- [x] **Баг: при прокрутке вверх нарисованный кадр стоял на месте** (жалоба на
      живой клиент).
      Кадр рисуется на том смещении, которое мы попросили, а колесо egui
      применяет уже после отрисовки, поэтому «просили» всегда на кадр позади.
      Якорь вида брался от «просили» и закреплял следующий кадр на прошлом
      месте; сверху его спасала проверка «прокрутил ли пользователь», но с
      медленным колесом (трекпад, хвост сглаживания) якорь доживал, и список
      стоял. Якорь теперь берётся от фактического места, где чат встал.
- [x] **Урок про тесты на прокрутке**: проверять надо нарисованный кадр, а не
      счётчик смещения. Счётчик уезжал правильно, а экран стоял — тест был
      зелёным на сломанном коде. В отладочную строку скролла добавлено поле
      `ask` (смещение, по которому нарисован кадр), и колесные тесты смотрят
      на него. Отдельно тест на медленное колесо: с быстрым поломка не
      проявлялась, и именно он её ловит.
- [x] **Баг: чат нельзя было листать** (жалоба на живой клиент, нашли тесты
      геометрии). Пока пользователь внизу, мы просили egui держать список на
      низу — и тут же затирали результат колеса на «дно», то есть стирали
      прокрутку в каждом кадре. Смещение уехать не могло: колесо, полоса
      прокрутки, перетаскивание — всё возвращалось назад. Удержание низа
      делается только тем смещением, которое мы просим (`vertical_scroll_offset`),
      состояние egui трогаем лишь когда едем вниз сами, а «прокрутил
      пользователь» определяется по тому, что список встал не туда, куда
      просили, и не на настоящий низ.
- [x] **Тест с настоящим колесом** (`wheel_scrolls_the_chat_in_both_directions`) —
      колесо через `RawInput` доводит список и до начала истории, и до низа.
      Отдельно проверка на голом `ScrollArea` без нашего кода: если и он не
      реагирует на колесо, дело в том, как мы кормим egui событиями, а не в
      чате. Такая проверка стоила дешевле, чем месяц гадания по симптомам.
- [x] **Баг: чат не докручивается до низа** (жалоба на живой клиент, нашли
      тесты геометрии). Пока пользователь внизу, длина списка всё равно
      меняется — уточняются высоты сообщений, приходят картинки, — а низ
      пересчитывался только в тот кадр, когда что-то пришло. Чат отползал
      от последнего сообщения, а новое сообщение его уже не тянуло: `chat_at_bottom`
      становился ложью. Теперь низ держится сам, пока пользователь внизу
      (`keep_at_bottom`), а порог «внизу» ужат с 12 до 1 px — иначе чат не
      отпускал бы его от низа после прокрутки на пять пикселей вверх.
- [x] **Баг: кадр, который едет вниз, рисовал верх канала** — список
      открывался на прошлом смещении (`chat_offset_y`), а не на том, для
      которого посчитанное окно сообщений. Видно было как вспышку при
      загрузке страницы. Теперь `vertical_scroll_offset` получает то же
      смещение, что и окно.
- [x] **Оценка высоты врала на +14% на каждое сообщение** (замер на живом
      egui: `LINE_H 16.5`, `BUBBLE_BASE_H 30`, `NAME_ROW_H 18`,
      `OTHER_MIN_H 72`, `IMAGE_GAP 6.0`, а стояло 18 и 63).
      Из-за этого длина списка плыла по мере прокрутки на сотни пикселей,
      и низ уезжал. Константы сняты замером, есть тест, который не даёт им
      снова разойтись с реальностью.
- [x] **Картинка больше не меняет высоту сообщения в момент загрузки**: размер
      (`width`/`height`) приходит от Discord вместе со ссылкой, место под
      картинку резервируется по нему, а не по заглушке 180 px. Заглушка
      осталась на случай, когда размера нет.
- [x] **Размер картинки из истории не доходил вообще** (находка из `BUGS.txt`).
      Правка выше поломки 0.5.1 не чинила: поле вложения было объявлено как
      JSON-`size`, а это размер файла в байтах, и `image_size_of` искал внутри
      этого числа ключи `width`/`height` — их там нет, поэтому `Attachment.size`
      у любого сообщения из истории был `None`. Живой путь разбора читал
      правильно, то есть два пути одного сообщения давали разный ответ, а
      тест на их согласие размер не сравнивал. Теперь в `RawAttachment` и
      `RawImage` настоящие поля `width`/`height`, а правило «что считается
      размером» живёт в одном `size_from` для обоих путей. Ровно эта ошибка
      стоила 180 px прыжка на каждое сообщение с картинкой при прокрутке.

### По `BUGS.txt` (части 4–5), после 0.5.1

Часть 4 (Б-1…Б-25) — поведение и надёжность, часть 5 (Т-1…Т-23) — цена кадра
и уборка. Закрыты все; подробности — в истории коммитов, здесь только то,
что стоит помнить. Тестов сейчас 175 (174 проходят, 1 — замер памяти).

- **Друзья**: запрос `/users/@me/relationships` вынесен в
  `fetch_relationships` с ретраем на 429 (по `retry-after`, до трёх попыток),
  разбор — чистый `parse_relationships`. Прежний запрос ловил 429 и молча
  оставлял список пустым.
- **Аватары и иконки**: отказ запоминается (`failed_avatars`) и повторно не
  качается; `AvatarFetch::{Ready, Failed, Busy}` различает «нет картинки» и
  «ещё не пробовали». Потолок списка сообщений — `trim_messages`.
- **Отладочные команды** переехали под `/debug `: обычный текст «/quit»
  больше не закрывает клиент, а «/add» не создаёт канал-призрак.
- **Смена аккаунта** чистит кэши картинок и аватаров и списки отказов —
  иначе на новом аккаунте мелькали аватарки прежнего.
- **Отпечаток клиента**: `os` берётся из `std::env::consts::OS` и в
  `X-Super-Properties`, и в IDENTIFY — раньше в рукопожатии по WebSocket
  было зашито «Linux», и Discord видел две разные системы у одного клиента.
- **История**: защита от дублей «запрос в полёте» живёт в `SessionState` и
  переживает реконнект; `content_h`/`est_h` в перемотке уже учитывают новое
  сообщение (посылка Т-20 не подтвердилась, стоит тест-сторож).
- **Длина сообщения**: счётчик `n/2000`, кнопка Send гаснет, поле не
  чистится — Discord больше не отвергает текст кодом 400 после «отправки».
- **Очередь гейтвея** разбирается порциями (`MAX_EVENTS_PER_FRAME = 200`):
  всплеск после реконнекта или разбуженный канал больше не подвешивает кадр.
- **Отладочный лог** в файл пишется только по `WYVERN_DEBUG`; в памяти
  `debug_log` ведётся всегда. Паника уходит в первый свободный
  `/tmp/wyvern_panic_N.log` вместе с бэктрейсом, стандартный хук сохранён.

### Замер: 300 сообщений + 32 картинки + гифка + 189 каналов

`cargo test --release -- --ignored --nocapture memcheck`

| Что | 0.4.0 | 0.5.0 |
|---|---|---|
| Пол (пустой клиент + кадр) | 9.7 МБ | 9.8 МБ |
| Разбор 300 сообщений: пик | 0.54 МБ / 4 517 | 0.54 МБ / 4 517 |
| Сообщения в памяти | 0.44 МБ | 0.44 МБ |
| Кэш картинок | 47.25 МБ | 47.25 МБ |
| Кэш с гифкой | 48.00 МБ | 48.00 МБ |
| 10 кадров (чат + списки) | 112 534 аллокаций | **32 827** |
| — только чат (300 сообщений) | 95 929 | **18 106** |
| — только списки (189 + 60) | 14 080 | 14 080 |
| RSS процесса | 84.9 МБ | **80.4 МБ** |
| Всего аллокаций за тест | 294 701 | 137 170 (−53%) |

Списки не изменились — 14 080 аллокаций на 10 кадров приходятся на них, а не
на чат, и трогать их нечем. Чат дал −81%: рисуются только видимые сообщения
плюс запас, вместо всех трёхсот.

На текущем коде (0.5.1) тот же замер даёт 138 947 аллокаций и RSS 76.5 МБ:
починка прокрутки и порядка хранения сообщений почти ничего не стоила.

**Вывод из замера:** «пол» — 9.8 МБ, сообщения — 0.44 МБ, кэш картинок —
48 МБ. То есть **93% памяти клиента — это кэш картинок**, и только он имеет
смысл ужимать дальше. Отрисовка перестала быть проблемой: 1.8 тыс. аллокаций
на кадр чата — это в основном сам egui (вёрстка и шрифт для каждой метки).

## Отклонено (проверено, выигрыш не стоит усилий)

- [ ] **`u64` вместо `String` в id.** Экономия ~35 КБ на 300 сообщений
      (8% занимаемой сообщениями памяти), а трогает гейтвей, приложение и
      все экраны: id ходят в URL, в ключи карт, в сравнения. Помечено
      отклонённым и в ROADMAP: выигрыш не стоит усилий.
- [ ] **`Arc<str>` для имён и контента.** Имена повторяются (30 авторов на
      300 сообщений) — выигрыш около 10 КБ. Помогает не памяти, а CPU, и
      тот клон убран вместе с клонами на кадр.
- [ ] **Два размера аватарок (32 и 64).** Кэш аватарок и так ограничен
      8 МБ, весь выигрыш — не больше 3 МБ.
- [ ] **Хеш вместо полных URL в `failed_images`.** Экономия 50 КБ, риск
      коллизий.
- [ ] **`MAX_MESSAGES_PER_CHANNEL` 500 → 150.** Выигрыш 350 КБ, история
      в канале станет короче втрое.
- [ ] **`u64`-хеш для `pending_images`** — то же самое, что и `failed_images`.
- [ ] **Чистить кэш картинок при смене канала.** Экономия — те самые 48 МБ,
      но все картинки канала придётся качать заново при возврате.
- [ ] **Кэшировать текст (Galley) для сообщений.** Оставшиеся ~1.8 тыс.
      аллокаций на кадр — это в основном сам egui (вёрстка и шрифт для
      каждой метки), а не наш код. Чтобы это убрать, надо писать свои
      виджеты вместо `ui.label`; выигрыш — CPU, не память. После
      виртуализации пункт стал втрое дешевле и потерял смысл.

      (`gateway.rs`).
- [x] **Ленивый hover**: подсказка строится в `on_hover_ui` только при
      наведении (`attachments.rs`).
- [x] **Инвалидация `msg_heights` по ширине окна**: кэш хранит `MsgHeight`
      (высота + ширина), после ресайза высота пересчитывается (`chat.rs`).
- [x] **File lock на vault**: решение — на всю сессию; при открытии хранилища
      берётся `flock` на файл-замок рядом с ним, второй экземпляр получает
      понятный отказ (`crypto.rs`).

      закрыт как not planned, а прокси ещё и отвечает 401 на часть путей.
      Остаётся локальное уменьшение до 768 px (`MAX_IMAGE_DIM`).
